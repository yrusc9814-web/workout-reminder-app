## 一、结论先行

当前版本可以作为视觉和流程原型继续迭代，但还不能作为可信的日常训练工具交付。最严重的问题不是页面是否好看，而是用户看到的计划、完成状态、统计和 AI 导入结果并不可靠：大量写操作只修改浏览器内存，刷新就丢；即使后续把前端 CRUD 接到后端，每次启动的自动 seed 仍会覆盖 2026-05 至 2026-08 的用户计划编辑。

综合判断：

- 产品成熟度：原型 / Demo，尚未达到可长期使用的个人工具。
- 数据可信度：不合格，存在刷新丢失、重启覆盖、重复完成和统计失真。
- 前端视觉：深色模式基础尚可；浅色模式照片透底、半透明内容卡和低对比辅助文字明显影响可读性。
- 交互完整度：原生弹窗过多，错误与成功反馈不一致，训练执行缺少真正的计时、休息倒计时和进度恢复。
- 动画：不是“动画太多”，而是缺少关键状态转换；只有 hover/宽度过渡和一个 AI pulse，页面切换、完成反馈、数字变化都很生硬。
- 测试：`123 passed`，但主要风险未被覆盖，绿灯不能代表产品闭环可用。

Fable 5 的报告不是“做得差”。它准确抓住了“前端写操作不落库”这一核心病灶，桌面视觉实测也有价值；但它漏掉了会改变修复顺序的更危险问题，并给出了一个不正确的 `template_id` 修法。因此，该报告适合做第一版方向稿，不适合直接作为实施和验收的唯一基线。

## 三、P0：必须先修的阻断问题

### P0-1 前端新增、编辑、删除和 AI 导入仍然不持久化

证据：

- `static/app.js:108-116`：`loadData()` 永远从 `defaultData()` 开始；`saveData()` 只更新时间和“API 缓存 KB”显示。
- `static/app.js:836-915`：动作、模板、计划、视频、删除和默认视频切换只修改内存 `state`。
- `static/app.js:1039-1079`：AI 草稿确认只合并到内存。
- 后端虽然已有 CRUD（如 `main.py:630`、`696`、`792`），前端保存流程没有调用它们。

用户影响：

- 新增动作、修改模板、编辑日期、添加视频、JSON 导入、AI 生成计划看起来成功，刷新后全部消失。
- Dashboard 完成率、连续训练、日历状态和 AI 分析都建立在易失内存上。
- “导入完成”“训练完成摘要”等成功反馈会制造错误信任。

验收条件：对每类资源执行“新增/修改/删除 → 刷新 → 重启服务”，结果仍存在；失败时不得先改 UI 再静默吞错。

### P0-2 服务启动会覆盖用户对种子月份的计划编辑

这是 Fable 报告遗漏的首要问题，也会改变实施顺序。

证据：

- `main.py:39-43`：服务启动时无条件调用 `seed_database()`。
- `database.py:350-390`：已有计划会被重写标题、训练类型、主题、备注和动作。
- `database.py:429-456`：每次 seed 都遍历 2026-05 至 2026-08 的每日计划。

已复现：把计划标题改为“用户自定义标题”，再次执行 seed 后恢复成默认标题。

用户影响：即使先完成 Fable 的 PR-01，把前端 CRUD 接到 API，用户的计划仍会在下次启动时被覆盖。因此必须先停止破坏性 reseed，再接前端保存。

正确修法：seed 只允许空库初始化或显式版本迁移；“恢复默认数据”必须是有确认、有备份、可审计的用户动作。

### P0-3 训练完成没有单一事实源，统计可重复、归零或超过 100%

证据：

- `database.py:39`：`WorkoutPlan` 没有持久化状态字段。
- `static/app.js:146`：API 计划进入前端时状态被无条件设为 `pending`。
- `static/app.js:728-755`：前端先把训练标为完成，再发送不等待结果的请求；`.catch(() => {})` 会吞掉网络错误，HTTP 422/500 也不检查。
- `main.py:389-406`：后端统计直接按日志条数计算，没有按计划/会话去重。
- `main.py:1164`：`/api/session/complete` 可重复调用并重复新增日志。

用户影响：同一次训练可能重复记账；刷新后又可能恢复“待开始”；统计既可能一直是 0，也可能超过实际完成次数。

正确修法：以 `WorkoutSession + SessionRecord` 为唯一训练事实源；完成接口幂等；计划状态由有效会话派生。不要同时让前端内存、Plan.status、WorkoutLog 和 WorkoutSession 四套状态各自为真。

### P0-4 SessionRecord 的动作引用语义已损坏

证据：

- `database.py:160`：`SessionRecord.exercise_id` 声称外键指向 `exercises.id`。
- `database.py:379`：seed 创建计划动作时没有填写 `WorkoutExercise.exercise_id`。
- `main.py:1138-1139`：为空时用 `WorkoutExercise.id` 冒充 `Exercise.id`。
- `database.py:30`：SQLite 没有启用 `PRAGMA foreign_keys=ON`。
- `main.py:1145`：session update 可用任意客户端 `exercise_id` 新建记录，不验证动作是否存在或属于当前计划。

当前数据库核验：265 条 `workout_exercises` 的 `exercise_id` 全为 `NULL`；动作库只有 ID 1-5，而 session 可生成 151-155 等孤儿引用，也接受 `exercise_id=999999`。

正确修法：SessionRecord 应引用具体计划动作快照（如 `workout_exercise_id`）；启用外键；更新前校验 session 状态、动作归属和唯一性。

## 四、P1：高优先级问题

### P1-1 后端失联时仍显示可信外观和假数据

证据：

- `static/app.js:38,61-111`：页面启动先渲染内置 5 个动作、1 个模板和假日程。
- `static/app.js:157-174`：合法空库或部分 API 失败会重新回退到默认数据，而不是诚实显示空状态。
- `static/app.js:300-305`：加载失败仍把 `startupState` 设为 `ready`。
- `static/index.html:46`：侧栏硬编码“后端数据源已连接”。
- 错误分支尝试修改 `#health`，但当前 HTML 没有该元素。

用户影响：后端挂掉、空库或 API 不完整时，用户仍看到一套貌似真实的训练计划和“已连接”状态。对健康/训练产品而言，这比普通错误页更危险。

建议：启动阶段只显示 skeleton；API 成功后才渲染真实数据；空库显示明确空状态；失败显示可重试 banner，绝不偷偷切到示例数据。示例数据只能通过“演示模式”显式进入。

### P1-2 JSON 导入预览存在 DOM XSS

证据：`static/app.js:924-940` 将导入动作名称组成 `exNames`，未经过 `escapeHtml()` 就拼进 `innerHTML`。

复现思路：导入动作名称包含 `<img src=x onerror=...>`，模板引用该动作，打开导入预览即可执行注入内容。

本项目虽然主要是本地单用户工具，但它支持粘贴 JSON 和 AI 生成草稿，同时 `run.py` 默认监听局域网，因此不能把这类注入视为无风险。

建议：所有外部数据必须在插入 HTML 前逐项转义；更稳妥的是使用 DOM API 创建文本节点。补一条恶意 JSON 的浏览器级回归测试。

### P1-3 训练执行页是“流程外观”，不是完整训练体验

证据：

- `static/app.js:655`：播放器 iframe 永远 `src="about:blank"`；外链能打开，但内嵌播放器承诺未兑现。
- `static/app.js:646-661`：计时型动作没有倒计时，进入休息只把状态改成 `resting`，没有休息时长、开始/结束提示或自动恢复。
- “自动切换下一个动作”实际上仍是手动点击按钮。
- 暂停或 resting 状态下，完成组/跳过等控制没有形成严格状态约束。
- session 只在内存中，刷新后无法恢复。

用户影响：真正训练时需要盯着页面外的计时器；误触和刷新会丢进度；“暂停”“休息”“自动切换”的文案与实际行为不一致。

建议：先明确训练状态机，再做 UI。最小状态为 `active → resting → paused → completed/cancelled`；计时动作与组间休息要有剩余时间、声音/震动可选、后台恢复和 reduced-motion 降级。

### P1-4 AI 的未配置、分析和反馈闭环仍然是断的

证据：

- `ai_service.py:245`：未配置 AI 时返回 `draft: null`。
- `static/app.js:1015`：前端无条件读取 `draft.exercises/templates/plans`，默认未配置场景会抛异常。
- `static/app.js:784`：“分析训练表现”只改一行状态文字，没有实际分析流程。
- `main.py:1178`：`/api/ai/feedback` 返回成功但不持久化。
- `ai_service.py:281`：分析输出没有 score/summary/adjustments schema 校验。
- `static/index.html:242` 仍显示“AI 辅助能力（第二阶段）”，与此前声称已移除第二阶段入口不一致。

建议：先修 `draft:null` 降级、输出 schema 和反馈落库，再前移 AI 入口。AI 未配置时仍应完成训练主流程，且不得显示“已生成/已导入”的假成功。

### P1-5 默认网络暴露和敏感调试信息边界不稳

证据：

- `run.py:4` 默认监听 `0.0.0.0`，但所有 CRUD、AI、通知接口无认证。
- `adapters/dingtalk.py:43,234` 的错误 trace 可能把含凭据的 webhook URL 带回 API 响应。
- 前端设置页直接展示钉钉“验收”和原始 JSON `<pre>`（`index.html:234-239`）。

建议：默认只绑定 `127.0.0.1`；远程模式必须显式开启并使用令牌；统一脱敏 URL 查询参数；把调试输出移到折叠的开发者模式。

### P1-6 时区策略在中国凌晨会选错“今天”

证据：

- `static/app.js:33` 使用 `toISOString()` 截取 UTC 日期。
- 后端用本地 `date.today()`；session 时间戳又用无时区 `datetime.utcnow()`。

在 Asia/Shanghai 00:00-07:59，前端日期可能比后端少一天，用户会看到错误的今日计划。

建议：业务日期统一采用配置的本地时区；持久时间戳使用 timezone-aware UTC。

### P1-7 通知失败会占用“已发送”去重槽位

`notification_service.py:53-107` 在未配置或发送失败时也记录 active 去重项。第一次返回 `not_configured` 后，第二次会变成 `duplicate_skipped`；之后即使补好凭据也不会自然重试。

建议：区分发送尝试和成功投递；只有成功才参与已发送去重，失败状态必须可重试。

## 五、前端界面、交互、动画与真实体验

### 5.1 视觉系统

做得好的部分：

- 有统一的颜色、圆角、间距、阴影和 motion 变量。
- 深色模式正文与辅助文字对比度较好。
- 图标使用 SVG，风格比 emoji 稳定。
- 有全局 `:focus-visible`，并提供 `prefers-reduced-motion` CSS 规则。
- 休息日文案温和、明确，不制造训练焦虑，是当前最有产品感的内容之一。

主要问题：

1. 浅色背景图透明度仍为 0.56（`styles.css:227-235`），内容卡仅 0.58 透明；照片纹理穿过正文，视觉焦点和对比度随背景位置变化。
2. 浅色 muted `#66758b` 在当前合成卡片背景上的对比度为 4.19:1，普通文本不达 AA。
3. 深色主题仍有 67 处 `body[data-theme='dark']` 逐组件覆盖（`styles.css:79-195`），主题不是纯 token 映射，维护时很容易漏一套。
4. 深色主按钮从绿色跳到青蓝渐变，品牌色跨主题不连续。
5. 顶栏把“API 驱动模式、后端状态机、记录同步”等开发术语放给普通用户，并用无功能的 WELCOME BACK 卡占据显著空间（`index.html:58-71`）。
6. Dashboard 继续堆叠 Hero、管理中心、5 张统计图、视频、周路线和整月日历（`index.html:75-99`），主任务“今天练什么”被管理入口和报表稀释。
7. 月度完成曲线仍被注入“今日相关视频”区域（`app.js:490-497`）；周计划和月历仍在 Dashboard 与独立页面重复。
8. 仪表盘三色段仍硬编码 23/35/42，旁边“全部⌄”不是可操作下拉（`app.js:445-457`），属于误导性装饰。
9. 月计划页文案承诺“统计概览”，但 `#monthStats` 被 `display:none !important` 隐藏（`styles.css:374-376`）。

视觉建议不是简单“换颜色”，而是重做层级：

- 内容层实底；照片只放 Hero 或降到不干扰阅读的装饰级。
- Dashboard 保留：今日 Hero、3 个真实指标、本周横条。管理入口移入导航，整月日历留在月计划页。
- 删除假仪表盘分段、假下拉和 WELCOME BACK。
- 浅深主题只映射语义 token，组件规则写一遍。

### 5.2 交互与反馈

- 全应用有 15 个 `alert()`、6 个 `confirm()`、1 个 `prompt()`；反馈会打断训练节奏，样式和可访问性也无法统一。
- AI 视频搜索仍要求输入动作 ID（`app.js:1098-1103`），这是开发者交互，不是用户任务语言。
- 页面切换只切换 `.active` 并重新 render（`app.js:342-348`），不更新 URL、浏览器历史和 `aria-current`；刷新和后退无法回到当前子页。
- 切页后没有把键盘/读屏焦点移到新页面标题，屏幕阅读器用户不知道内容已变化。
- 后端完成请求失败仍展示完成摘要；这是比“没有 toast”更严重的反馈一致性问题。
- 空状态和错误状态混在示例数据 fallback 里，用户无法判断“真的没有数据”还是“服务不可用”。

建议用统一反馈层：顶部连接 banner、字段旁 inline error、非阻断 toast、危险动作 `<dialog>`。所有成功反馈必须以后端确认或可追踪的本地离线队列为前提。

### 5.3 动画与状态转换

现状：

- 唯一 `@keyframes` 是 AI 生成步骤的 pulse（`styles.css:653-661`）。
- 页面是 `display:none/block` 瞬切（`styles.css:343-344`），没有进入/退出过渡。
- 进度条、仪表针、hover 有 180-200ms 过渡，时长合理。
- 完成本组没有独立成功反馈；数字变化没有稳定数字宽度或 count-up。
- `prefers-reduced-motion` 能压缩 CSS 动画，但 AI 入口的 `scrollIntoView({behavior:'smooth'})`（`app.js:783`）仍会强制平滑滚动。

建议：只增加三类有信息价值的动画：页面/面板 120-180ms 淡入、完成本组的局部确认、数字/进度的状态变化。休息倒计时应以可读数字为主，不依赖持续旋转。reduced-motion 下禁用 JS 平滑滚动和非必要缩放。

### 5.4 响应式与可访问性

1. 小于 1200px 时 sidebar 变成页面顶部，但两个 `<details open>` 保持展开；在 375px 宽度，用户先经过品牌、8 个导航、3 个 AI 动作和状态卡，才看到“今天练什么”。移动端首屏优先级完全倒置。
2. 多个按钮/导航项高度约 30-40px；移动触控未达到 44px/48dp 目标。
3. 周计划和日历在手机上变成横向滚动的大表格，缺少明确的可滚动提示和聚焦策略。
4. 图表多为 SVG + 颜色，缺少统一的文本替代摘要和读屏角色。
5. 原生 dialog 是正确方向，但动态标题没有显式 `aria-labelledby`；切换页面和关闭 dialog 后也没有焦点回返策略。

建议：移动端只保留紧凑顶部栏和底部/折叠菜单，首屏必须直接出现今日计划。触控目标至少 44px；新增 `aria-current`、live region、焦点管理和图表文本摘要。

## 六、测试与架构质量

测试全部通过，但存在“字符串出现就算接入”的假阳性：

- `tests/test_static_contract.py:10,85` 主要检查 JS 中是否存在端点字符串，无法证明调用时机、payload、错误处理和落库结果。
- `tests/test_static_contract.py:340` 名为“不自动覆盖 localStorage”的测试只断言存在 `confirm` 字样。
- `tests/test_v31_prd.py:18` 的 AI feedback 闭环测试不检查 `ai_feedback` 是否真的落库。
- `tests/test_api.py:884` 只测试整数 template ID；`partial` 测试不检查它被错误写成 skipped。

必须补的测试：

- 新增/编辑/删除/AI 导入后刷新与重启仍存在。
- seed 重启不覆盖用户数据。
- session 动作外键有效，非计划动作返回 422。
- session complete 幂等；不存在计划日期不返回 500。
- 后端失联不显示假数据和“已连接”。
- AI `draft:null`、畸形分析结果和 feedback 真落库。
- 通知失败后可重试。
- UTC+8 凌晨前后端日期一致。
- 恶意 JSON 导入预览不会执行 HTML/脚本。
- 375px、键盘、reduced-motion 的浏览器级验收。

架构上不要先机械拆 `main.py`。先统一领域模型和事实源，再拆 router/service/repository；否则只是把双轨状态分散到更多文件。

## 八、建议的正确实施顺序

### Gate 0：先止血和保护数据

1. 备份数据库；停止自动覆盖已有计划的 seed。
2. 明确 Exercise、WorkoutExercise、SessionRecord 的引用关系并迁移数据。
3. 开启 SQLite 外键，补唯一约束和 session complete 幂等。
4. 统一业务时区和本地绑定安全默认值。

验收：重启不改用户数据；无孤儿记录；重复 complete 只记一次。

### Gate 1：建立单一事实源

1. 以 SQLite + WorkoutSession 为事实源。
2. 前端 CRUD、JSON/AI 导入和训练 session 全部接 API。
3. 移除隐式 defaultData fallback，增加 loading/empty/error/offline 明确状态。
4. 所有成功反馈以后端确认或可靠离线队列为前提。

验收：新增/编辑/完成训练经刷新和重启仍一致；断后端不显示假数据。

### Gate 2：训练体验闭环

1. 增加计时动作、组间休息、暂停/恢复和刷新续练。
2. 视频要么真正嵌入并处理失败，要么删除空 iframe，只保留明确外链。
3. 训练完成后展示可信摘要，并可回看记录。

### Gate 3：视觉、交互和可访问性

1. Dashboard 减到 1-1.5 屏，内容卡实底化。
2. 删除假图表/假下拉/开发术语；设置页拆出开发者区。
3. 替换原生 alert/confirm/prompt；补移动首屏、44px 触控、焦点、ARIA 和 reduced-motion。

### Gate 4：AI 闭环

1. 先处理未配置/失败降级和 schema。
2. 草稿事务落库、feedback 真正落库。
3. 再做“完成训练 → 小结 → 建议 → 应用到下次计划”。

只有 Gate 0-1 完成后，AI 和视觉投入才不会继续建立在不可信数据上。
