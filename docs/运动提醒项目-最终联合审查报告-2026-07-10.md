## 1. 最终结论

当前项目已经具备较完整的产品外观、训练计划概念、深浅主题、动作与模板管理、提醒和 AI 草稿入口，但本质上仍是一个视觉与流程原型，尚未达到“可以长期信任的个人训练工具”标准。

阻止交付的首要问题不是界面美观，而是数据真实性：

- 动作、模板、计划、视频、JSON 导入和 AI 草稿确认主要只修改前端内存，刷新后丢失。
- 即使把前端 CRUD 接到后端，服务启动时的自动 seed 仍会覆盖种子月份内的用户计划编辑。
- 训练完成同时存在前端内存、WorkoutLog、WorkoutSession/SessionRecord 等多套状态，统计可能归零、重复或失真。
- SessionRecord 的动作引用已经存在语义损坏，数据库外键也未启用。
- 后端失联、空库或部分接口失败时，页面仍可能展示一套貌似真实的默认计划，并硬编码“后端数据源已连接”。

因此，正确方向不是立即继续堆 UI 或 AI 功能，而是先完成数据止血和单一事实源，再升级训练体验、视觉和 AI 闭环。

### 当前成熟度判断

| 维度 | 结论 |
|---|---|
| 产品定位 | 个人训练计划原型，方向成立 |
| 数据可信度 | 不合格，存在刷新丢失、重启覆盖、重复记录 |
| 训练执行体验 | 不完整，缺计时、休息倒计时、续练和真正的视频内嵌 |
| 桌面视觉 | 深色模式基础较好；浅色可读性和信息密度需要重构 |
| 移动端 | 有响应式规则，但首屏优先级、触控目标和横向表格体验不合格 |
| AI 能力 | 有安全意识和草稿概念，但未形成可用闭环 |
| 测试可信度 | 123 项通过，但大量是静态字符串契约，不能证明真实流程可用 |
| 交付状态 | 不建议作为正式日常训练工具发布 |

## 4. P0：必须先修的阻断问题

### 4.1 前端仍是“只读 API + 易失内存态”

证据：

- `static/app.js:108` 的 `loadData()` 永远从 `defaultData()` 开始。
- `static/app.js:113` 的 `saveData()` 只更新 `updatedAt` 和容量显示，不写 localStorage，也不调用后端。
- 动作、模板、计划、视频、删除和默认视频切换集中在 `static/app.js:836-915`，都只修改内存 `state`。
- AI 草稿确认位于 `static/app.js:1039-1079`，仍只合并内存数据。
- 后端虽然存在 Exercise、Template、Plan CRUD，但前端保存路径没有调用它们。

结果：

- 用户看到“保存”“导入完成”“训练完成摘要”，但刷新后结果消失。
- Dashboard 的完成率、连续训练、日历完成状态和 AI 分析都建立在不可靠状态之上。
- JSON 导入和 AI 生成计划看似功能完整，实际不能成为长期数据。

验收标准：动作、模板、计划、视频、JSON/AI 导入分别执行“新增或修改 → 刷新 → 重启服务”，结果必须保持一致；失败时不得先显示成功再静默吞错。

### 4.2 自动 seed 会覆盖用户编辑

这是联合审查中最重要的新增发现，会直接改变 Fable 原路线的实施顺序。

证据：

- `main.py:39-43`：服务启动无条件调用 `seed_database()`。
- `database.py:350-390`：已有计划会被重写标题、训练类型、主题、备注和动作。
- `database.py:429-456`：每次 seed 遍历 2026-05 至 2026-08 的所有日期。

复现结果：把种子日期标题改为“用户自定义标题”，重新执行 seed 后恢复默认标题。

结论：不能先做“前端 CRUD 接 API”。必须先停止覆盖式 seed，否则刚修好的后端持久化仍会在重启时丢失。

正确方案：

- seed 仅用于空库初始化或显式版本迁移。
- 已存在用户行不得被普通启动流程更新。
- “恢复默认数据”改为明确、可确认、先备份的管理操作。
- 引入正式 migration，不能继续依赖 seed 兼任迁移。

### 4.3 完成状态没有单一事实源

证据：

- `WorkoutPlan` 没有可靠的持久状态字段。
- `static/app.js:146` 将 API 计划状态无条件设为 `pending`。
- `static/app.js:728-755` 先在前端标完成，再发送不等待结果的请求；`.catch(() => {})` 吞掉网络错误，HTTP 422/500 也未检查。
- 后端统计直接数日志行，没有按计划或会话去重。
- `/api/session/complete` 可对同一 session 重复调用并重复新增日志。

正确方案：

- `WorkoutSession + SessionRecord` 成为唯一训练事实源。
- 完成接口必须幂等，并有明确状态转换。
- 计划状态从有效 session 派生，而不是同时存在前端 state、Plan.status、WorkoutLog 和 WorkoutSession 四套真相。
- WorkoutLog 只保留审计用途，由 session complete 自动生成且具唯一键。

### 4.4 SessionRecord 引用关系已损坏

证据：

- `database.py:160` 声称 `SessionRecord.exercise_id` 指向 `exercises.id`。
- seed 创建 `WorkoutExercise` 时没有填写真正的 `exercise_id`。
- `main.py:1138-1139` 在缺失时用 `WorkoutExercise.id` 冒充动作库 ID。
- SQLite 外键未启用。
- session update 允许客户端提交任意 `exercise_id`，不验证动作是否存在、是否属于计划或 session 是否已完成。

当前数据库核验：265 条计划动作全部未关联动作库；动作库只有 ID 1-5，但 session 可生成 151-155 等孤儿引用，也接受 `999999`。

正确方案：

- SessionRecord 引用具体计划动作快照，例如 `workout_exercise_id`。
- 迁移现有数据并启用 `PRAGMA foreign_keys=ON`。
- 校验动作归属、session 状态和重复记录。
- 同一计划只允许一个活动 session，完成后禁止继续 update。

### 5.3 Dashboard

Fable 实测 Dashboard 总高约 2600px，而视口为 900px，需要接近 3 屏滚动。当前结构仍包括：

- 今日 Hero。
- 管理中心 4 卡。
- 5 张月度统计图。
- 今日相关视频。
- 本周训练路线。
- 完整月历。

具体问题：

1. 今日任务不是唯一焦点，管理入口、统计和月历抢占大量空间。
2. 月度完成曲线仍被注入“今日相关视频”面板。
3. 周路线和完整月历在 Dashboard 与独立页面重复。
4. 仪表盘三色段硬编码为 23/35/42，与真实完成率没有语义关系。
5. “整体进度 全部⌄”看起来是下拉，但不能操作。
6. 顶栏向普通用户展示“API 驱动模式、后端状态机、记录同步”等开发术语。
7. WELCOME BACK 卡占据显著宽度，却没有任何任务价值。

目标结构：

- 第一层：今日 Hero，清楚回答“今天练什么、多久、现在能做什么”。
- 第二层：3 个真实指标——本月完成率、连续训练、本周完成进度。
- 第三层：一条紧凑的本周路线。
- 管理中心放入导航；完整月历只保留在月计划页。
- 目标：1440×900 下总高不超过 1350px，即约 1.5 屏。

### 5.4 今日训练、月计划和设置页

今日训练：

- 休息日文案优秀，但内容区过空，可加入恢复建议、轻活动计时和明日预告。
- 训练日动作列表同时塞入名称、剂量、链接、benefit、备注，层级不足。
- 应明确区分动作名称、训练剂量、要点和视频操作。

月计划：

- 页面文案承诺“统计概览”，但 `#monthStats` 被 `display:none !important` 隐藏。
- 日历状态依赖不持久的前端状态，完成标记不可信。
- 手机端是宽表横向滚动，缺少滚动提示和聚焦策略。

设置页：

- JSON 导入导出、主题、钉钉验收、原始 JSON、AI 全部堆在一个长页面。
- “钉钉提醒验收”“AI 辅助能力（第二阶段）”是开发阶段语言。
- 调试输出应进入折叠的开发者模式。
- 用户设置与集成测试应拆开。

### 5.5 浅色与深色主题

浅色模式是视觉重灾区：背景照片 opacity 0.56、ambient 光斑和 58% 半透明内容卡叠加，使文字可读性随照片区域变化。内容层应实底化，照片只留在 Hero 或降到装饰级。

深色模式视觉基础较好，但当前 CSS 仍有约 67 处 `body[data-theme='dark']` 组件级覆盖，并同时出现 `.theme-dark` 和 `[data-theme='dark']` 两套选择器。应收敛为语义 token 映射，组件规则只写一次。

推荐原则：

- 浅色内容卡使用 `#fff` 或接近实底的 surface。
- 深色内容卡使用稳定的 `#1c2438` 一类 surface。
- 背景照片不应穿过长段正文。
- 品牌主色保持同一色相，只调整明度和饱和度。
- 全站只保留两档卡片阴影和明确的 card/control 圆角。

## 6. 交互、动画、响应式与可访问性

### 6.1 反馈系统

当前 `app.js` 包含：

- 15 个 `alert()`。
- 6 个 `confirm()`。
- 1 个 `prompt()`。

问题不只是“不够好看”：

- 原生弹窗打断训练节奏。
- 不能统一处理 loading、成功、失败和重试。
- AI 视频搜索要求用户输入动作 ID，是开发者交互而不是用户任务语言。
- 训练完成请求失败仍可能展示成功摘要。

建议统一为：

- 全局连接 banner：后端离线、数据同步失败。
- inline error：表单字段和 AI 草稿校验。
- toast：非阻断成功和普通错误。
- `<dialog>`：删除、覆盖导入、结束训练等危险确认。
- 所有成功提示以后端确认或可靠离线队列为前提。

### 6.2 页面导航

当前切页只是切换 `.active` 后重新 render：

- URL 和浏览器历史不变化。
- 刷新、后退不能回到当前子页。
- nav 没有 `aria-current`。
- 切页后焦点没有移到新页面标题。

建议至少采用 hash 路由，保存当前页面并支持后退；切页后将焦点移动到新页面标题，同时更新 `aria-current="page"`。

### 6.3 动画

当前动画不是过多，而是不完整：

- 唯一 `@keyframes` 是 AI 生成过程的 pulse。
- 页面通过 `display:none/block` 瞬切。
- hover、进度条和仪表针有 180-200ms 过渡，时长合理。
- 完成本组、完成训练和数字变化缺少局部状态确认。
- CSS reduced-motion 有效，但 JS `scrollIntoView({behavior:'smooth'})` 仍强制平滑滚动。

只建议增加三类有信息价值的动画：

1. 页面/面板 120-180ms 淡入。
2. 完成本组和训练完成的局部确认。
3. 进度和数字变化的短过渡。

reduced-motion 下禁用 JS 平滑滚动、非必要缩放和持续动画。

### 6.4 移动端

小于 1200px 时 sidebar 变成页面顶部，但辅助工具和系统状态的 `<details open>` 继续展开。375px 宽度下，用户会先经过品牌、8 个导航、3 个 AI 操作和状态卡，才看到今日计划，首屏优先级完全倒置。

其他问题：

- 多个按钮和导航高度约 30-40px，未达到 44px/48dp 触控目标。
- 周计划和月历变成横向滚动宽表，没有明确提示。
- 顶栏、欢迎卡和全部设置内容在窄屏仍占较大高度。

移动端目标：紧凑顶部栏 + 折叠菜单或底部导航；打开页面第一屏直接看到今日计划和主 CTA。

### 6.5 可访问性

已有优点：语义 button、原生 dialog、全局 focus-visible、部分 aria-live 和 reduced-motion CSS。

仍需补：

- 切页和 dialog 关闭后的焦点管理。
- `aria-current`、连接状态 live region、错误 `role="alert"`。
- 图表的文本摘要和明确读屏角色。
- 动态 dialog 的 `aria-labelledby`。
- 触控目标至少 44px。
- 对比度、键盘操作、最大字体和 375px 浏览器级回归。

## 7. 训练执行体验

当前训练执行页具备动作、组数、完成本组、跳过、暂停和摘要的外形，但状态机和体验仍未完成：

- iframe 始终是 `about:blank`，实际只有 Bilibili 外链可用。
- 计时型动作没有倒计时。
- “进入休息”只把状态改成 `resting`，没有时长、结束提示或自动恢复。
- “自动切换下一个动作”实际上仍是手动按钮。
- paused/resting 状态没有严格限制完成组、跳过等操作。
- session 只在内存中，刷新无法恢复。
- 完成接口失败也可能显示成功摘要。

最小状态机建议：

`ready → active → resting → active → paused → active → completed/cancelled`

必须具备：

- 计时动作倒计时和组间休息倒计时。
- 暂停时冻结计时和动作操作。
- 刷新后恢复活动 session。
- 视频真正嵌入并处理失败，或删除空 iframe、明确只提供外链。
- 完成后以后端确认的 session 数据生成摘要。
- AI 不可用时仍能完成全部基础训练流程。

## 8. AI 能力

### 已有正确方向

- AI 只生成 draft，不直接静默覆盖正式数据。
- Bilibili 域名白名单和 YouTube 黑名单有安全意识。
- import-plan 有一定 schema 校验和人工确认。
- 未配置时没有伪造模型结果。

### 当前断点

- 未配置 AI 时后端返回 `draft: null`，前端却无条件读取 `draft.exercises/templates/plans`。
- AI 草稿确认只修改内存，刷新丢失。
- “分析训练表现”入口只修改一行状态文字，没有真实流程。
- `/api/ai/feedback` 返回成功但不落库。
- `WorkoutSession.ai_feedback` 字段存在却没有完整写入管道。
- 分析输出没有 `score/summary/adjustments` 结构校验。

正确顺序：

1. 修复未配置和失败降级。
2. 给分析输出加严格 schema。
3. 草稿通过单事务导入端点落库。
4. feedback 和 AI 小结真正写入 session。
5. 再建设“完成训练 → 小结 → 下次建议 → 一键应用”的闭环。

不要在 Gate 0-1 数据问题未解决前继续增加聊天或复杂 Agent 功能。

## 9. 后端、通知与安全

### 9.1 `/api/training/complete` 不应只改 template_id 类型

Fable 指出的类型不匹配部分正确：默认前端使用 `'core_stability'`，后端声明 `int | None`，可返回 422。

但简单改成 `str | None` 不是正确修复：

- 正常 API 模板 ID 是可转为整数的字符串。
- `template_id` 在端点中实际上未参与核心逻辑。
- 不存在计划的日期可能触发数据库错误。
- 非 done 状态可能被错误归为 skipped。

应废弃该旁路端点，或把它适配到正式 plan/session 状态机，要求有效 plan/session 并验证枚举。

### 9.2 通知失败去重

当前 NotificationService 在成功、失败或未配置时都可能写 active 记录。第一次返回 `not_configured` 后，第二次就可能 `duplicate_skipped`，补好凭据也无法自然重试。

正确方案：区分 attempt 和 delivered；只有成功投递才参与已发送去重，失败保留可重试状态。

### 9.3 默认网络边界

- `run.py` 默认监听 `0.0.0.0`。
- CRUD、AI、通知接口无认证。
- 客户端可传通知强制参数。
- 钉钉网络错误 trace 可能包含完整 webhook URL。

默认应只绑定 `127.0.0.1`；远程模式需显式开启并使用令牌；日志和 API 响应统一脱敏 URL 查询参数。

### 9.4 时区

前端以 `toISOString()` 计算今日，后端使用本地 `date.today()`，session 时间戳又使用无时区 UTC。Asia/Shanghai 00:00-07:59 可能出现前后端日期差一天。

业务日期统一使用配置的本地时区；持久时间戳使用 timezone-aware UTC。

## 10. 测试为何全绿但产品仍不可用

现有测试的主要缺陷是把“代码里出现端点字符串”当作“功能已经接入”：

- `tests/test_static_contract.py` 大量断言只检查 HTML/CSS/JS 字符串。
- 命名为“不自动覆盖 localStorage”的测试只检查存在 `confirm` 字样。
- AI feedback 闭环测试没有检查 `ai_feedback` 真正落库。
- training complete 只覆盖整数 template ID。
- partial 测试没有验证最终日志是否被错误写成 skipped。

必须补充：

- 新增/编辑/删除/JSON/AI 导入后刷新和重启仍存在。
- seed 重启不覆盖用户数据。
- seed 计划的 SessionRecord 引用有效。
- 非计划动作 update 返回 422。
- session complete 幂等。
- 不存在计划日期不返回 500。
- 后端失联不显示假数据和“已连接”。
- AI `draft:null`、畸形分析输出、feedback 真落库。
- 通知失败后可重试。
- UTC+8 凌晨日期一致。
- 恶意 JSON 预览不执行 HTML/脚本。
- 375px、键盘、reduced-motion 和深浅主题浏览器级验收。

## 12. 每个 PR 的最终审查清单

通用：

- 刷新和重启后数据是否保持。
- API 非 2xx 是否有可见错误和恢复动作。
- 是否存在裸 `.catch(() => {})`。
- payload、response model 和测试是否同步。
- AI 未配置时基础训练是否仍可用。
- 深浅主题、375px、键盘和 reduced-motion 是否验证。

数据与 Session：

- seed 是否绝不覆盖用户行。
- foreign_keys 是否开启。
- ID 迁移后模板、计划动作、视频和 session 引用是否一致。
- session 是否只接受计划内动作。
- complete 是否幂等，完成后是否禁止 update。
- 统计是否按唯一计划/session 计算。

前端与视觉：

- loading、empty、error、offline 是否互相区分。
- 成功反馈是否以后端确认或可靠离线队列为依据。
- 内容卡是否实底，浅色 muted 是否 ≥4.5:1。
- 是否删除假图表、假下拉、重复日历和开发术语。
- 触控目标是否 ≥44px。
- 切页、dialog、错误和动态状态是否有正确焦点/ARIA。

AI：

- `draft:null` 和超时是否可降级。
- 畸形 JSON 是否被 schema 拒绝。
- 草稿导入是否单事务，失败不得写入一半。
- feedback 和 ai_feedback 是否真的写入数据库。
- AI 调用不得阻塞基础训练完成。

安全：

- 默认是否只监听回环地址。
- URL、Webhook、token 是否脱敏。
- JSON/AI 内容进入 innerHTML 前是否全部转义。
- 无认证远程模式是否被禁止。

## 13. 最终判断

这个项目的方向是成立的：本地个人训练、康复向低强度内容、钉钉提醒和 AI 辅助组合有明确使用场景；休息日文案、主题系统、动作/模板/计划概念也形成了不错的产品底子。

但当前最大矛盾是“界面已经像产品，数据仍像 Demo”。用户会因为页面完成度而相信计划、统计和 AI 结果已经保存，而系统实际上可能在刷新或重启后丢失、覆盖或重复计算。这种“看起来成功”比直接报错更需要优先修复。

最终执行原则只有一句：

**先让每一条数据可信，再让训练流程完整，之后才投入视觉精修和 AI 教练化。**
